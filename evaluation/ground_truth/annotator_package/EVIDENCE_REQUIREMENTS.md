# 证据填写要求

每个关键判断都要能回答：谁发布的、原文在哪里、哪句话支持结论、适用于什么条件、使用的是哪个时间和版本。

## 怎样算有效证据

来源身份可追溯、原文可定位、与目标和条件对应，并直接支持当前判断。例如，维护者原公告明确写出相同包、分支的受影响范围，可以支持对应的版本范围判断；仍须核对被问版本是否在范围内。

博客猜测、搜索摘要、仓库名、视频标题、模型生成的解释只可作为线索，不能单独确认影响或利用成功。相关页面不一定是支持证据；发布时间相近也不是关联证明。

## 来源优先级

| 等级 | 常见来源 | 使用边界 |
|---|---|---|
| L1_OFFICIAL | 厂商/维护者原公告、官方发行说明和补丁、CNA/CVE/NVD 正式记录 | 优先用于明确事实；仍查包、分支、时间和直接性 |
| L2_RESEARCH | 可识别作者的安全研究、经过审阅的公告库、可溯源技术分析 | 补充与交叉核对；确认实际发布者和引用关系 |
| L3_SECONDARY | 博客、转载、未知作者仓库、二次总结 | 发现线索，或明确保存为候选，不单独确认重要结论 |

等级按发布者与来源链判断，不只看域名。GitHub 平台上的任意仓库不自动是官方来源。两篇转引同一公告的文章不算独立证明。高等级也不自动产生高置信度或确认状态。

## 时间字段使用实际模板名称

日常交流中的“来源、URL、原文、时间”，在本项目分别对应 `source_name`、`url`、`quote`，以及 `published_time/retrieved_time/time_note`。**模板没有一个通用的 time 字段，不自行新增。**

下方是现有模板的空证据片段，仅展示填写位置；没有实际来源，不能计为一条有效证据。

```json
{
  "evidence_id": "",
  "source_name": "",
  "source_id": "",
  "url": "",
  "quote": "",
  "locator": "",
  "canonical_excerpt": "",
  "snapshot_sha256": null,
  "authority_level": null,
  "published_time": null,
  "retrieved_time": null,
  "time_note": "",
  "role": null,
  "judgment_ids": []
}
```

## 每项填写什么

| 字段 | 填写方法 |
|---|---|
| evidence_id | 表单内唯一的证据编号，供判断引用 |
| source_name | 实际发布者或资料名称，不能把转载者写成原发布者 |
| source_id | 当前冻结目录中真实登记的来源 ID；新来源需管理员另行登记冻结 |
| url | 实际原来源 HTTPS 地址，不用搜索结果页、虚构地址或带凭据的链接 |
| quote | 原文短片段，保留必要前后文与条件；翻译另作说明，不冒充原文 |
| locator | 现有冻结 JSON 中的非空 JSON Pointer，以 `/` 开头；需能定位原文对应值 |
| canonical_excerpt | 定位值的规范 JSON，由管理员或现有资料提供后核对；不能用改写段落替代 |
| snapshot_sha256 | 对应冻结源文件的哈希，不是网页 URL、问题或整份答案的哈希 |
| authority_level | 按实际来源选 L1_OFFICIAL、L2_RESEARCH 或 L3_SECONDARY |
| published_time | 资料真实发布时间；无法确认可为 null，并写 time_note |
| retrieved_time | 实际获取时间，不能代替发布时间；使用带时区的日期时间格式 |
| time_note | 时间未知、更新、不同页面时序差异等说明 |
| role | SUPPORTING（支持）、CONTRADICTING（反证）、CONTEXTUAL（背景） |
| judgment_ids | 实际关联判断 ID，与 judgments 中的 evidence_ids 双向一致 |

时间由实际查源人员记录，使用 RFC 3339 的带时区格式，可采用北京时间 `+08:00` 或 UTC `Z`。不要复制文档整理日期作为查源或复核时间。

## 原文与定位怎样对应

`quote` 供人阅读，`canonical_excerpt` 供后续冻结引用核对。前者必须是定位资料中的原文，后者必须与相应 JSON Pointer 的值一致；它们不是同一种文本。

当前候选包可以帮助找到指针、原文和来源哈希，不能因为已经整理过就认定支持判断。若冻结投影缺少所需事实，应阅读原始来源并向管理员报告；不能把投影里不存在的文字写成已冻结引用。

选择新的维护者公告、commit 或其他资料时，由管理员后续保存新快照并登记新来源。它不在旧 manifest 中时，不借用旧 source_id，也不覆盖旧来源文件。本次说明文档没有完成这些新增登记。

## 证据怎样支持判断

把每个关键答案拆成 `judgments`，记录 `answer_path`、结论、理由和证据 ID。只说明“与漏洞有关”的资料应标背景，不标支持。明确相反内容应标反证并保存冲突。

没有直接依据时写清缺失信息和调查范围，保留未知；不能因“没有搜到”得出“不存在”。未知答案仍需可核对资料和完整缺口说明，不能用空证据占位来取得批准。

对补丁，区分发现 commit 与确认修复；对 POC，区分候选与既有合法独立验证材料。本轮不执行攻击代码，也不从仓库名推断验证成功。

## 提交前核对

- URL 指向实际资料，编号、组件和条件与问题对应。
- 原文包含结论所需条件，未隐去例外、分支或反证。
- 发布时间与获取时间分开，未知时间有说明。
- 证据 ID、判断 ID、定位、摘录和哈希对应。
- 你亲自打开并核对了来源；候选包和 HTTP 成功没有被当成人工确认。
