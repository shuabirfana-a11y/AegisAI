# 常见错误与修正方法

以下是一般性的操作提醒，不是当前 49 题的答案。遇到同类问题，记录实际证据与缺口，按[标注手册](ANNOTATOR_TASK_MANUAL.md)和[复核手册](REVIEWER_TASK_MANUAL.md)处理。

| 常见错误 | 为什么有问题 | 正确处理 |
|---|---|---|
| 根据 CVSS 判断某版本受影响 | 严重程度评分不能说明被问版本是否在影响范围内 | 查对应包、生态、分支和版本范围 |
| 根据 CVSS 直接判断生产资产风险 | 缺少资产配置、可达性、攻击前提和防护条件 | 分别核对影响和资产条件；本批政策题只评价声明政策 |
| 根据 CVE 编号、标题或 ID 后缀猜答案 | 编号和 affected/fixed 等命名不是证据 | 阅读原问题与原公告，保留不确定 |
| 公告没提某版本，所以判 NOT_AFFECTED | 缺少信息不等于明确排除 | 找覆盖该版本的可靠排除或修复依据，否则未知 |
| 把 `<` 看成 `<=`，忽略多分支或区间空档 | 会改变被问版本的实际判断 | 原样保存范围并核对分支、生态和边界 |
| 发现 POC 仓库就填 VERIFIED_EXPLOIT | 相关代码或 README 不能证明独立验证成功 | 无既有合法验证记录时保留候选或证据不足 |
| 参考列表有 commit 就填 CONFIRMED_FIX | 引用关系不等于补丁验证 | 记录 PATCH_CANDIDATE，查清 release/commit 的确认范围 |
| 根据博客确认漏洞影响或修复 | 二次资料可能遗漏条件或转述错误 | 追溯原始发布者，博客保留为线索或候选 |
| 证据不足但为了有答案强行确认 | 标准答案本身会污染评测 | 写 UNKNOWN/INSUFFICIENT_EVIDENCE 和缺口，允许正确弃答 |
| 没搜到 POC 就写“世界上不存在 POC” | 检查范围有限，不能证明普遍不存在 | 记录 NO_EVIDENCE 及范围，后续映射为 UNKNOWN |
| 直接复制 AI 或机器参考答案 | 无法证明人独立查源，也会让评测偏向既有输出 | 人亲自查原来源；如使用 AI 辅助，诚实留痕 |
| HTTP 200 或编号匹配就认为证据支持结论 | 只能证明资源可读与身份匹配 | 逐条检查原文是否支持当前判断 |
| 把转载页面当作额外独立证据 | 两份文字可能都来自同一原资料 | 保存来源链，独立证据按实际来源判断 |
| 把获取时间当发布时间 | 会错误判断公告与修复时序 | 分别填 published_time、retrieved_time，未知写 time_note |
| 翻译或总结后当原文 quote | 复核人无法在来源中逐字找到 | 保存原文，翻译作为辅助说明 |
| 用一个旧 source_id 指向新来源 | 来源、定位与冻结哈希无法对应 | 报给管理员另行登记冻结，不覆盖旧文件 |
| 两个账号由同一人操作，或用 AI 当复核人 | 不满足两个不同真人独立审核 | 登记真实可追溯团队 ID，每题安排不同真人 |
| 复核意见只写“同意”或只检查有没有漏填 | 不能证明原文支持结论 | 亲自查源、完整读答案与证据、逐项签核并写意见 |
| 为了通过校验预填人名、确认和时间 | 伪造了实际工作和审核记录 | 未完成副本可暂不通过，不冒充完成的 HUMAN_RECORD |
| 把 ANNOTATING 或 EXPORT 写进人工表单状态 | 原人工 Schema 没有这些枚举 | ANNOTATING 记任务卡，导出用独立字段和台账 |
| 批准后直接改答案或套用旧审核哈希 | 复核人没审核过改动后的内容 | 新修订、新内容哈希、重新复核，保留原件 |
| 空模板、资料包或任务卡计为已标注 | 没有形成真人答案 | 人工填写、复核、批准数量分别统计 |
| 一道 POC/Patch 复合题算成两条样本 | 重复计数并夸大覆盖 | 一份记录按字段关联证据，只计一个原 ID |
| 把 APPROVED 当成已冻结、已评测或答案全被确认 | 人工流程批准、导出准入和业务判断是不同事情 | 保存批准原件，另查来源与字段准入，不提前报准确率 |

有争议时保留双方依据、标明需要补查的事项。不能删掉反证、降低复核要求或改变题目来让记录更容易通过。
