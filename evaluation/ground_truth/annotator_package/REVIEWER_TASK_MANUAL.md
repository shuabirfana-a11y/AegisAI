# 第二复核人员操作手册

你的工作是独立检查一份标准答案是否可信。不必另写完整答案，但必须亲自阅读原始资料，检查完整答案与全部证据。你必须与该题标注人是不同自然人。

## 接收什么

接收原问题及完整输入、人工表单路径、修订号、内容哈希和资料入口。先确认 ID 和题目一致，再看答案。不要把机器参考答案、系统输出或模型得分当裁决依据。

管理员应锁定送审版本。若复核过程中有人改了答案或证据，停止对旧内容签署；改动需新修订、新哈希和重新复核。

## 单题复核流程

1. **读问题和条件。** 检查包名、生态、版本、分支、资产输入及政策要求；不要根据文件名猜结论。
2. **自己打开原来源。** 阅读引用前后文，核对来源身份、时间、冻结定位和资料版本。仅能打开 URL 不代表支持答案。
3. **逐项看答案与判断。** 每个关键字段都检查 `judgments` 与 `evidence` 的关联，完整读完，不只看摘要或标注人挑出的部分结论。
4. **检查过度推断和未知。** 例如，有仓库链接只能证明发现线索，不能直接证明利用有效；公告缺信息时不强迫给确定结论。
5. **填写检查表与意见。** 按下表逐项核对，记录实际阅读范围、问题和分歧。条目不适用时在 `review_note` 写明原因，不能直接跳过或批量勾选。
6. **明确批准或退回。** 真实填写你的团队 ID、审核时间、查源确认和审核内容哈希；管理员核对后保存对应版本并同步台账。

## 各类题最容易漏什么

**版本题：** 原文是 `<` 还是 `<=`，是否有多个修复分支、预发布或区间空档；一个分支已修复不代表其他分支都安全。未提供版本时，不允许猜部署版本。

**事实题：** CVSS 版本、向量和评分是否对应；缺失不能写成已确认零风险。描述与原文一致，不能把标题改写成未经证实的影响。

**Patch/POC 题：** commit 在参考列表中不等于已验证补丁。README 提到 CVE 不等于已验证利用。没有既有合法独立验证材料时，保留候选或证据不足；本轮不执行 PoC。

**风险/多跳题：** 当前题按声明政策核对，不能当生产资产专家风险判断。每个资产和中间步骤分别有依据，未知资产不能被其他已知资产的结论覆盖。

## 怎样写复核意见

批准时写明检查的资料、关键边界、处理的不确定性和不适用项。只写“同意”或“看过了”无法说明审核范围。

退回时写清：有问题的答案字段、涉及的证据 ID、原文支持不足或矛盾点、需要补查的材料。事实存在冲突但无法解决时，不替标注人删掉反证来达成批准。

`review_note` 保存完整复核意见；`rejection_reason` 在退回时记录具体原因。实际查源后才设置 `reviewer_confirmed_source_check=true`。填写实际 `review_started_at`、`reviewed_at`，不要提前签署或使用文档生成时间。

审核绑定 `reviewed_content_sha256`，必须等于当前 `content_sha256`。管理员可帮助计算和核对，复核人仍需确认它对应自己读过的修订。

## 什么可以批准

两位真实成员独立完成、证据与字段合格、检查表逐项完成、意见与哈希绑定一致的记录，才可 `APPROVED`。

合理的 `UNKNOWN` 或 `INSUFFICIENT_EVIDENCE` 可以批准，前提是调查范围、可核对资料和缺口足够清楚。批准记录不等于确认漏洞受影响、利用成功或补丁有效。

格式通过只能证明结构，不能证明人真的参与、证据支持答案或风险判断可靠。证据不合格、身份不独立、输入被改或审核绑定错误时退回；存在未解决的实质分歧时保持待复核或按理由退回。

本轮不把批准记录直接交给评测器。导出准入、来源冻结和评分口径由管理员后续另查，参见[完整流程](LABELING_PROCESS.md)。
