你现在负责 AegisAI 项目的第 1 阶段：

【需求调研与需求冻结】

注意：这一阶段不要写任何正式代码，不要搭数据库，不要做前端，不要接 Dify，也不要开始采集数据。

你的任务是把赛题要求转化成一份可以直接指导后续开发的《产品需求文档 PRD》。

==================================================
一、项目背景
==================================================

项目暂定名称：

AegisAI——面向 AI 生态的可信安全情报系统

项目核心目标：

持续监测多个公开安全信息源，
发现与 AI 生态相关的漏洞和安全事件，
对原始信息进行标准化、去重、富化和核验，
形成可信安全情报，
并通过智能体支持复杂安全问答、风险分析和处置建议。

系统主流程暂定：

多源信息
→ 采集
→ 标准化
→ 去重
→ 实体统一
→ 版本解析
→ AI安全相关性判断
→ 情报富化
→ 多源核验
→ 可信情报库
→ 持续跟踪
→ 资产匹配
→ 风险分析
→ 智能问答

但不要直接把这个流程当成最终答案。

你需要结合赛题文件重新验证和完善。

==================================================

==================================================

找到当前项目目录中赛题原始 PDF / Word / Markdown 等文件。

完整阅读。

不要只依赖已有总结。

从赛题原文提取：

1. 赛题背景
2. 明确要求

4. 可选能力

10. 官方提供的平台、账号、培训、API或数据
11. Agent相关要求
12. 自动化相关要求
13. 工程化相关要求
14. 性能指标
15. 准确率指标
16. 演示要求

每一项注明：

【赛题明确要求】

还是：

【我们自己的设计】

不能混在一起。

==================================================
三、把评分表反向转换成开发需求
==================================================

这是本阶段最重要的工作。

不要只写：

“需要多源监测。”

而要转成可验收需求。

例如：

赛题要求多源监测

转换成：

REQ-MON-001

系统必须支持多个异构安全数据源。

验收方式：

后台可以展示当前启用的数据源；
每个数据源显示最后同步时间；
能够展示真实采集记录。

--------------------------------------------------

赛题要求监测时效

转换成：

REQ-MON-002

每条情报必须保存：

source_published_at
retrieved_at

系统能够计算：

retrieved_at - source_published_at

用于统计采集延迟。

--------------------------------------------------

赛题要求情报富化

转换成：

REQ-ENRICH-001

系统应能够围绕漏洞补充：

CVSS
CWE
Affected Product
Affected Version
Fixed Version
Vendor Advisory
POC
Patch
Technical Analysis
Paper
Asset Impact

但必须根据赛题原文区分：

哪些属于明确要求，
哪些属于我们为了提高完成度增加。

==================================================
五、需求分级
==================================================

所有需求分为：

P0 —— 必须完成

如果没有，系统无法满足赛题核心要求。

P1 —— 高价值增强

明显提升评分、完整性或者Demo效果。

P2 —— 决赛增强

时间允许或进入决赛后完成。

P3 —— 暂时不做

投入大、收益低或者偏离赛题。

==================================================
